# 11. 스토어 앱 빌드 (GitHub Actions) — 개발자가 빌드하고 DODA 스토어 계정에 올리기

> 이 안내서는 개발자(Eric)가 실행하는 절차예요. DODA 는 스토어 계정을 만들고 관리자 권한을 주는 일, 콘솔에서 운영 설정을 켜는 일만 해요. 빌드, 서명, 배포는 DODA 가 하지 않아요.
> Developer-run guide. DODA owns the store accounts and grants admin access; DODA does no technical work.

## 0. 큰 그림

- 빌드는 **개발자의 GitHub 저장소** [EricWijesinghe/Dahae](https://github.com/EricWijesinghe/Dahae) 의 워크플로 **`store-apps`** 가 해요 (수동 실행, `workflow_dispatch`).
  - 안드로이드 AAB: Linux 러너 (ubuntu)
  - iOS IPA: macOS 러너. 공개 저장소의 GitHub 호스티드 러너는 무료예요.
- 만든 AAB 는 **DODA 의 Google Play Console** (내부 테스트 트랙 초안), IPA 는 **DODA 의 App Store Connect** (TestFlight) 로 올라가요.
- DODA 는 Apple 조직 계정과 Play 조직 계정을 소유하고, 개발자에게 **관리자(Admin)** 권한을 줘요. 개발자는 이 권한으로 키를 만들고 앱을 올려요.
- DODA 에 추가 비용이 없어요.
- 저장소는 공개예요. 키, 비밀번호, `.p8`, keystore 는 저장소에 올리지 않아요. 모든 비밀값은 GitHub 환경 **`store`** 의 Secrets 에만 넣어요.
- 시작 전에 서면 라이선스 계약이 있어야 해요 (저장소 `LICENSE` §1.4·§3.1, [LAUNCH-PLAN](../LAUNCH-PLAN.md) §7).

## 1. 역할

| 일 | 누가 |
|---|---|
| Apple Developer Program 을 **조직**으로 가입, D-U-N-S 번호, 계약 동의, App Store Connect API **액세스 요청** (한 번) | DODA (계정 소유자) |
| Play Console **조직** 가입, D-U-N-S 번호 | DODA |
| 개발자 Apple ID 를 Apple 조직의 **Admin** 멤버로 초대 | DODA 가 초대, 개발자가 수락 |
| 개발자 Google 계정을 Play Console 에 **관리자** 로 초대 | DODA 가 초대, 개발자가 수락 |
| App ID, 앱 두 개, App Store Connect API 키, 서비스 계정, keystore, GitHub 시크릿 | 개발자 (관리자 권한으로) |
| 서버 콘솔에 결제·문자 키 입력 | 사장님이 [직원]에서 개발자에게 관리자 계정을 만들어 주면 문자·푸시·로그인 카드는 개발자가 처음 저장할 수 있어요. PortOne·토스 카드, 잠금 해제, 저장 뒤 연결 확인은 사장님 계정만 돼요. |
| 첫 AAB 의 Play 수동 업로드 | 개발자 |
| 심사 제출 | 개발자 (DODA 직원도 같은 권한으로 제출할 수 있어요) |

## 2. 계정 준비 (DODA 가 만들고 개발자에게 권한을 줘요)

**Apple** (DODA)
1. developer.apple.com 에서 **조직** 가입, D-U-N-S 번호 필요, 연 99 USD ([guide 03](03-앱-출시.md) A).
2. Users and Access 에서 개발자 Apple ID 를 **Admin** 으로 초대해요.

**Google Play** (DODA)
1. play.google.com/console 에서 **조직** 계정 가입 ([guide 03](03-앱-출시.md) B).
2. 개발자 Google 계정을 **관리자**로 초대해요.

**Firebase, 간편 로그인, PortOne, Solapi** (DODA 소유) 는 DODA 가 가입하고, 개발자에게 접근 권한을 줘요. 키를 넣는 곳은 [DEPLOY.md](../DEPLOY.md) §3 표를 봐요.

## 3. GitHub 설정 (개발자 저장소)

1. 저장소 **Settings → Environments → New environment** → 이름 **`store`**. 승인자(Required reviewers)는 필요할 때만 켜요.
2. **Environment variables** (`store`): `API_BASE` = `https://<도메인>` (예: `https://app.example.co.kr`). 앱에 첫 주소가 들어가요. `APPLE_TEAM_ID` = Apple 팀 ID (10자). `APP_LINK_DOMAIN` = 서버 도메인 (`https://` 없이, 예: `app.example.co.kr`). 도메인을 옮긴 뒤에는 `새도메인,예전도메인` (쉼표, 세 개까지).
   선택: `CUSTOMER_APP_ID`, `PARTNER_APP_ID` = 스토어 앱 ID (기본 `kr.co.dahae.customer`, `kr.co.dahae.partner`). 다른 회사 이름으로 스토어에 올릴 때 **첫 업로드 전에** 정해요. 바꾸면 새 앱이 돼요.
   앱 이름(홈 화면), 아이콘, 색은 빌드할 때 서버(`API_BASE/v1/brand`, 콘솔에 저장한 값)에서 받아요. 콘솔에 로고를 먼저 저장하세요. 서버에 연결되지 않으면 빌드가 멈춰요 (`brand_from_server` 를 끄면 저장소의 이름과 아이콘으로 빌드해요).
3. **Environment secrets** (`store`), 이름을 **대소문자까지 그대로** 입력:

| 이름 | 값 | 필수 |
|---|---|---|
| `ANDROID_KEYSTORE_B64` | 업로드 keystore 파일을 base64 로 바꾼 값 ([4번](#4-안드로이드-업로드-키-한-번만)) | 안드로이드 |
| `ANDROID_KEYSTORE_PASSWORD` | keystore 비밀번호 | 안드로이드 |
| `ANDROID_KEY_ALIAS` | `upload` | 안드로이드 |
| `ANDROID_KEY_PASSWORD` | 키 비밀번호 | 안드로이드 |
| `GOOGLE_PLAY_SERVICE_ACCOUNT_JSON` | Play 서비스 계정 JSON 파일 내용 전체 ([5번](#5-google-play-콘솔-doda-조직-개발자-관리자)) | 자동 업로드 |
| `ASC_KEY_ID` | App Store Connect API 키의 Key ID | iOS |
| `ASC_ISSUER_ID` | App Store Connect Issuer ID | iOS |
| `ASC_KEY_P8_B64` | `.p8` 파일을 base64 로 바꾼 값 | iOS |
| `GOOGLE_SERVICES_JSON_B64` | 고객 안드로이드 Firebase 설정 파일을 base64 로 | 푸시·구글 로그인 |
| `GOOGLE_SERVICE_INFO_PLIST_B64` | 고객 iOS `GoogleService-Info.plist` 를 base64 로 | 푸시 (iOS) |
| `PARTNER_GOOGLE_SERVICES_JSON_B64` | 파트너 안드로이드 설정 파일 | 파트너 푸시 |
| `PARTNER_GOOGLE_SERVICE_INFO_PLIST_B64` | 파트너 iOS 설정 파일 | 파트너 푸시 |
| `KAKAO_NATIVE_KEY` | 카카오 네이티브 앱 키 | 카카오 로그인 |
| `NAVER_CLIENT_ID` | 네이버 Client ID (**Client Secret 은 넣지 마세요**. 서버만 써요) | 네이버 로그인 |
| `NAVER_CLIENT_NAME` | 네이버 앱 이름 | 네이버 로그인 |
| `GOOGLE_SERVER_CLIENT_ID` | 구글 웹 OAuth Client ID | 구글 로그인 |
| `GOOGLE_IOS_CLIENT_ID` | 구글 iOS OAuth Client ID (고객 앱 번들 ID) | 구글 로그인 (iOS) |
| `PARTNER_GOOGLE_IOS_CLIENT_ID` | 구글 iOS OAuth Client ID (파트너 앱 번들 ID). iOS 클라이언트는 번들 ID 하나에만 묶여요 | 파트너 앱 구글 로그인 (iOS, 앱 심사) |
| `SOCIAL_PROVIDERS` | 선택. 예: `kakao,naver` | 선택 |

- 값이 없는 선택 항목은 빈칸으로 두면 돼요. 그 기능의 버튼이 숨겨지거나 푸시가 꺼진 채 빌드돼요. 빌드는 실패하지 않아요.
- base64 는 암호화가 아니에요. 값을 붙여 넣을 때 줄바꿈이 없어야 해요 (PowerShell: `[Convert]::ToBase64String([IO.File]::ReadAllBytes("파일경로"))`).
- 키 목록의 정확한 이름은 `.github/workflows/store-apps.yml` 과 `scripts/ci/native-keys.sh` 가 기준이에요. 이름을 바꾸면 이 표도 같이 고쳐요.

## 4. 안드로이드 업로드 키 (한 번만)

1. 개발자 PC 에서 keystore 를 만들어요 (비밀번호는 비밀번호 관리 앱에 저장).

```
keytool -genkeypair -v -keystore dahae-upload.jks -alias upload -keyalg RSA -keysize 2048 -validity 10000
```

2. `dahae-upload.jks` 를 base64 로 바꿔 `ANDROID_KEYSTORE_B64` 에 넣어요. 비밀번호와 alias 도 넣어요.
3. **원본 파일을 두 곳에 따로 보관하세요** (외장 드라이브 + 비밀번호 관리 앱). 잃어버리면 Play 업데이트가 막혀요. 복구는 Play 고객지원을 거쳐야 해요 (확인 필요).
4. Play App Signing 은 기본으로 켜져 있어야 해요 (앱 만들 때 기본값).

## 5. Google Play 콘솔 (DODA 조직, 개발자 관리자)

1. Play Console 에서 앱 두 개를 만들어요: `kr.co.dahae.customer` (다해), `kr.co.dahae.partner` (다해 파트너).
2. **첫 AAB 는 사람이 직접 올려요** (Google Play API 로는 첫 릴리스를 만들 수 없어요).
   - `store-apps` 를 `platform` = `android`, `upload` 끔으로 실행하고, 결과의 AAB 아티팩트를 내려받아요.
   - Play Console → 앱 → **테스트 → 내부 테스트** → 새 버전 만들기 → AAB 업로드 → 저장 → 검토 → 출시.
3. **서비스 계정 (자동 업로드용)**: Google Cloud 콘솔 → **IAM 및 관리자 → 서비스 계정** → `eric-play-upload` 만들기 → 그 프로젝트에서 **Google Play Android Developer API** 사용 설정 → JSON 키 생성. 그다음 Play Console → **사용자 및 권한 → 새 사용자 초대** → 서비스 계정 이메일 → 두 앱에 출시 권한을 줘요. JSON 파일 내용 전체를 GitHub 환경 `store` 의 시크릿 `GOOGLE_PLAY_SERVICE_ACCOUNT_JSON` 에 넣어요. (Play Console 의 "API 액세스" 화면이나 Cloud 프로젝트 연결은 이제 필요 없어요.)
   - 이름 규칙: 개발자를 위해 만드는 계정·키는 모두 이름에 `eric` 을 넣어요. DODA 가 누구 것인지 알 수 있게요.
4. 이후 빌드는 내부 테스트 트랙에 **초안(draft)** 으로 올라가요. Play Console 에서 확인하고 출시(승격)해요.
5. 첫 업로드 뒤 **Play 앱 서명 인증서의 SHA-1** 을 Play Console → 설정 → 앱 무결성에서 복사해, 카카오·구글 콘솔에 등록해요 ([DEPLOY §3](../DEPLOY.md)). 같은 화면의 **SHA-256** 은 서버 콘솔 **설정 → 앱 링크** 의 "안드로이드 서명 지문 (SHA-256)" 칸에 넣어요 (없으면 안드로이드 네이버 로그인이 앱으로 돌아오지 않아요).

## 6. Apple App Store Connect (DODA 조직, 개발자 관리자)

1. developer.apple.com → Identifiers 에서 App ID 두 개: `kr.co.dahae.customer`, `kr.co.dahae.partner`. **Push Notifications, Sign in with Apple, Associated Domains 세 개를 모두** 켜요. 하나라도 빠지면 서명이 실패해요.
2. App Store Connect → 앱 → **+ 새 앱** 으로 두 앱을 만들어요 (번들 ID 는 위와 같게, 언어 한국어). 앱 레코드가 있어야 TestFlight 업로드가 돼요.
3. **App Store Connect API 키**: Users and Access → Integrations → App Store Connect API → **Team Keys** → 키 생성 (역할 **Admin**. App Manager 키는 자동 서명 내보내기에서 "Cloud signing permission error" 로 실패해요). 이 화면은 DODA 계정 소유자가 API 액세스를 요청한 뒤에 열려요 (1번 표).
   - `.p8` 파일은 **한 번만** 내려받을 수 있어요. 안전하게 보관하세요.
   - Key ID → `ASC_KEY_ID`, Issuer ID → `ASC_ISSUER_ID`, `.p8` 을 base64 로 바꾼 값 → `ASC_KEY_P8_B64`.
4. 인증서와 프로필은 직접 만들지 않아요. 워크플로가 이 API 키로 자동 발급해요 (확인 필요: 첫 실행 로그에서 확인).
5. **APNs 키 (푸시)**: Keys → Apple Push Notifications service 에서 `.p8` 를 만들고, Firebase → 프로젝트 설정 → Cloud Messaging → Apple 앱 구성에 앱마다 올려요.
6. 서버 콘솔 **설정 → 앱 링크** 카드에 Apple **Team ID** 를 넣어요 (Membership 화면).

## 7. Firebase 와 로그인 키 (선택)

- Firebase 는 DODA 소유예요. 개발자가 접근 권한으로 프로젝트에 들어가 앱 설정 파일을 받아 base64 로 바꿔 넣어요 (3번 표).
- 카카오·네이버·구글 콘솔 등록 절차는 [DEPLOY.md §3](../DEPLOY.md) 과 [guide 03](03-앱-출시.md) B-2 를 봐요.
- 서버 쪽 키(푸시 서비스 계정, 결제, 문자)는 **서버 콘솔 설정 마법사**에 넣어요. GitHub 에 넣지 않아요 ([guide 02](02-설정-마법사.md)).

## 8. 빌드 실행

1. 저장소 **Actions → store-apps → Run workflow**.
2. `app`: `customer`, `partner`, `both`. `platform`: `android`, `ios`, `both`.
   - `upload` 를 **끄면** 빌드만 하고 결과 파일 (아티팩트) 만 남아요. 올리려면 **켜세요**. 첫 Play 업로드는 끈 상태로 AAB 를 받아서 손으로 올려요 (5번).
   - 버전 이름은 가장 최근 `vX.Y.Z` 태그를 따라요 (태그가 없으면 pubspec.yaml). 릴리스 태그를 만든 뒤에 실행하세요.
3. 결과:
   - Android: AAB 가 아티팩트로 남고, `upload` 를 켰으면 Play 내부 테스트 트랙에 초안으로 올라가요.
   - iOS: `upload` 를 켰으면 IPA 가 App Store Connect 로 올라가요. Apple 처리에 10~30분 걸려요. TestFlight 에 빌드가 보여요.
4. 빌드 번호는 자동으로 올라가요 ([scripts/ci/build-number.py](../../scripts/ci/build-number.py)). 직접 정하지 마세요.
5. 첫 실행 전 확인: `API_BASE` 변수가 맞는지, 시크릿 이름이 표와 같은지.

## 9. 확인과 심사

1. **iOS**: TestFlight 내부 테스터(개발자, DODA 직원)가 실기기에서 확인해요. 로그인(전화, 카카오, 네이버, 구글, Apple), 사진, 결제창, 푸시, 위치.
2. **Android**: Play 내부 테스트 초안을 확인하고 휴대폰에 설치해 확인한 뒤 출시(승격)해요.
3. **심사 제출은 사람이 해요.** 워크플로는 심사에 자동으로 보내지 않아요.
   - App Store Connect: 버전에 빌드 추가 → [review-notes.md](../store/review-notes.md) 를 심사 메모에 붙여 넣기 → [app-privacy.md](../store/app-privacy.md) 대로 개인정보 라벨 → 제출. 두 앱 모두.
   - Play: [data-safety.md](../store/data-safety.md), [play-declarations.md](../store/play-declarations.md) 답변을 확인하고 심사에 보내요.
4. 심사 전에 서버가 떠 있어야 해요. 심사원은 데모 계정으로 로그인해요. 데모 계정은 DODA 관리자가 콘솔 **설정 → 스토어 심사용 데모 계정** 에서 켜고, 번호와 코드를 심사 메모에 적어요 (14일 뒤 자동으로 꺼져요, [guide 03](03-앱-출시.md) D).

## 10. 업데이트

0. 콘솔에서 이름·로고·색·앱 ID·도메인을 바꿨다면 콘솔의 **스토어 앱 빌드** 카드가 알려 줘요. 이런 값은 새 빌드에만 들어가요.
1. 새 버전 태그 (예: `v1.6.1`) 를 만들고 `store-apps` 를 다시 실행해요.
2. Android: Play Console 에서 초안 확인 → 출시. iOS: TestFlight 확인 → 심사 제출.
3. 스토어 심사와 출시가 끝나면 휴대폰이 자동으로 업데이트해요.

## 11. 자주 막히는 곳

| 증상 | 원인과 해결 |
|---|---|
| 앱이 서버에 연결되지 않음 | `API_BASE` 변수가 없거나 틀려요. 고친 뒤 다시 빌드해요 |
| iOS 서명 실패 | App ID 세 개 기능 중 하나가 꺼져 있어요 ([6번 1항](#6-apple-app-store-connect-doda-조직-개발자-관리자)) |
| Play 업로드 권한 오류 | 서비스 계정에 두 앱의 출시 권한이 있는지 확인해요 |
| 첫 Play 업로드가 API 로 안 돼요 | 정상이에요. 첫 AAB 는 Play Console 에서 직접 올려요 ([5번 2항](#5-google-play-콘솔-doda-조직-개발자-관리자)) |
| 카카오·구글 로그인 실패 (Android) | Play 앱 서명 SHA-1 이 카카오·구글 콘솔에 없어요 ([5번 5항](#5-google-play-콘솔-doda-조직-개발자-관리자)) |
| 푸시가 안 와요 | `GoogleService-Info.plist` 또는 APNs 키가 빠졌어요 ([guide 03](03-앱-출시.md)) |

## 12. 아직 확인하지 않은 것

- Xcode 26.6 은 macOS 26 러너 이미지에 들어 있어요 (actions/runner-images 기준). 그래도 첫 실행 로그에서 한 번 확인해요.
- 인증서·프로필 자동 발급, iOS 카드 앱 복귀 (PortOne 웹 결제), 용량: 실제 첫 빌드에서만 알 수 있어요.

## English

> Developer-run guide. DODA owns the Apple organization and the Play organization and gives the developer admin access. DODA does no build, signing or deployment work; it only creates accounts, grants access and handles console settings.

### 0. Overview

- The developer runs the **`store-apps`** workflow (manual, `workflow_dispatch`) in the repository [EricWijesinghe/Dahae](https://github.com/EricWijesinghe/Dahae). Android AAB runs on ubuntu; iOS IPA runs on macOS. GitHub-hosted runners are free for this public repository.
- The AAB goes to DODA's Google Play Console (internal testing draft); the IPA goes to DODA's App Store Connect (TestFlight).
- Secrets live only in the GitHub environment **`store`**. Keys, passwords, `.p8` and keystores are never committed.
- A signed written license is required before the work starts (`LICENSE` §1.4 and §3.1; [LAUNCH-PLAN](../LAUNCH-PLAN.md) §7).

### 1. Roles

| Task | Who |
|---|---|
| Apple Developer Program as an organization, D-U-N-S, agreements, App Store Connect API **access request** (once) | DODA (account holder) |
| Play Console organization, D-U-N-S | DODA |
| Invite the developer's Apple ID as **Admin**; invite the developer's Google account as an administrator | DODA invites, developer accepts |
| App IDs, the two apps, App Store Connect API key, Play service account, keystore, GitHub secrets | Developer (with admin access) |
| Payment and SMS keys in the server console | Once the owner creates an admin account for the developer under Staff, the developer can make the first save of the SMS, push and sign-in cards. The PortOne and Toss cards, unlocking, and the connection check after saving work only from the owner account. |
| First Play AAB upload by hand | Developer |
| Review submission | Developer (DODA staff may submit with the same access) |

### 2. Accounts

- **Apple**: DODA enrolls as an organization (D-U-N-S required, 99 USD per year, [guide 03](03-앱-출시.md) A). DODA invites the developer's Apple ID as **Admin**.
- **Google Play**: DODA registers an organization account ([guide 03](03-앱-출시.md) B) and invites the developer as an administrator.
- **Firebase, social sign-in, PortOne, Solapi**: owned by DODA; the developer gets access. Key table: [DEPLOY.md §3](../DEPLOY.md).

### 3. GitHub setup (developer repository)

1. Settings → Environments → **New environment** named **`store`**. Required reviewers are optional.
2. Environment **variables**: `API_BASE` = `https://<domain>` (the first address baked into the app), `APPLE_TEAM_ID` (10 characters), `APP_LINK_DOMAIN` (bare host; after a domain move `new,old`, three at most). Optional: `CUSTOMER_APP_ID`, `PARTNER_APP_ID` (store app ids, default `kr.co.dahae.*`; set before the first upload, a new id is a new app). The home-screen name, icons and colour come from the server (`API_BASE/v1/brand`) at build time; the build stops if the server cannot be read (input `brand_from_server` off uses the repo's name and icons).
3. Environment **secrets** (`store`), names exactly as written:
   - Android: `ANDROID_KEYSTORE_B64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS` (`upload`), `ANDROID_KEY_PASSWORD`, `GOOGLE_PLAY_SERVICE_ACCOUNT_JSON` (for automatic uploads)
   - iOS: `ASC_KEY_ID`, `ASC_ISSUER_ID`, `ASC_KEY_P8_B64`
   - Native keys (optional; a missing value hides that feature, the build still passes): `GOOGLE_SERVICES_JSON_B64`, `GOOGLE_SERVICE_INFO_PLIST_B64`, `PARTNER_GOOGLE_SERVICES_JSON_B64`, `PARTNER_GOOGLE_SERVICE_INFO_PLIST_B64`, `KAKAO_NATIVE_KEY`, `NAVER_CLIENT_ID`, `NAVER_CLIENT_NAME`, `GOOGLE_SERVER_CLIENT_ID`, `GOOGLE_IOS_CLIENT_ID`, `PARTNER_GOOGLE_IOS_CLIENT_ID`, `SOCIAL_PROVIDERS`
   - **Never** put `NAVER_CLIENT_SECRET` here. The server uses it.
   - The authoritative names are in `.github/workflows/store-apps.yml` and `scripts/ci/native-keys.sh`.
   - base64 has no encryption: paste it without line breaks.

### 4. Android upload key (once)

```
keytool -genkeypair -v -keystore dahae-upload.jks -alias upload -keyalg RSA -keysize 2048 -validity 10000
```

Base64-encode the file into `ANDROID_KEYSTORE_B64`, and add the passwords and alias. Keep the original file in two separate places. Losing it blocks Play updates; recovery goes through Play support (to be confirmed). Play App Signing stays on (the default).

### 5. Google Play Console (DODA organization, developer as administrator)

1. Create `kr.co.dahae.customer` and `kr.co.dahae.partner`.
2. **The first AAB is uploaded by hand.** Run `store-apps` with platform `android` and upload off, download the AAB artifact, and upload it to Internal testing → create release → review → roll out. The Play API cannot create the first release.
3. **Service account** (for automatic uploads): Google Cloud console → **IAM & Admin → Service accounts** → create `eric-play-upload` → enable the **Google Play Android Developer API** for the project → create a JSON key. Then Play Console → **Users and permissions → Invite new users** → the service account's email → release permissions on both apps. Paste the full JSON into the GitHub environment `store` secret `GOOGLE_PLAY_SERVICE_ACCOUNT_JSON`. (The Play Console "API access" page and linking a Cloud project are no longer needed.)
   - Naming rule: every account or key made for the developer has `eric` in its name, so DODA can see whose it is.
4. Later builds appear as **drafts** on the internal track. Check them and promote.
5. After the first upload, copy the **Play app-signing SHA-1** (Setup → App integrity) and register it in the Kakao and Google consoles. Put the SHA-256 from the same page into Settings → App links (Android fingerprint); without it Android Naver sign-in does not return to the app.

### 6. Apple App Store Connect (DODA organization, developer as admin)

1. App IDs `kr.co.dahae.customer` and `kr.co.dahae.partner`: enable **Push Notifications, Sign in with Apple and Associated Domains** on both. Signing fails if one is missing.
2. Create the two App Store Connect apps (bundle IDs as above, language Korean). The record must exist before the first TestFlight upload.
3. **API key**: Users and Access → Integrations → App Store Connect API → Team Keys, role **Admin** (cloud signing needs it). The page opens only after DODA's Account Holder has requested API access (table in step 1). The `.p8` downloads **once**. Key ID → `ASC_KEY_ID`, Issuer ID → `ASC_ISSUER_ID`, base64 of the `.p8` → `ASC_KEY_P8_B64`.
4. Certificates and profiles are not made by hand; the workflow creates them with this key (to be confirmed on the first run).
5. **APNs key**: create it under Keys, and upload it to Firebase → Cloud Messaging → Apple app configuration for each iOS app.
6. Put the Apple **Team ID** in the server console under **Settings → App links**.

### 7. Firebase and sign-in keys (optional)

Firebase belongs to DODA; the developer uses granted access to download the config files and base64-encode them. Server-side keys go into the **setup wizard** of the server console ([guide 02](02-설정-마법사.md)), not into GitHub.

### 8. Run the build

1. **Actions → store-apps → Run workflow**. `app`: `customer`, `partner` or `both`. `platform`: `android`, `ios` or `both`. `upload` off builds and keeps the artifacts only; turn it on to upload. The version name is the newest `vX.Y.Z` tag (no tag: pubspec.yaml); create the release tag first.
2. Android: the AAB is an artifact, and with `upload` on it becomes a draft on the internal track. iOS: with `upload` on, the IPA goes to App Store Connect; Apple processing takes 10–30 minutes.
3. Build numbers are set by [scripts/ci/build-number.py](../../scripts/ci/build-number.py). Never set them by hand.

### 9. Checks and review

1. **iOS**: TestFlight internal testers check on real devices (sign-in, photos, payment window, push, location).
2. **Android**: check the internal-track draft on a phone, then promote.
3. **Submission is manual.** Paste [review-notes.md](../store/review-notes.md), fill App Privacy from [app-privacy.md](../store/app-privacy.md), submit both apps. For Play use [data-safety.md](../store/data-safety.md) and [play-declarations.md](../store/play-declarations.md).
4. The server must be running before review. DODA turns on the demo account in the console (**Settings → Review demo account**) and writes the number and code into the review notes. It turns off after 14 days ([guide 03](03-앱-출시.md) D).

### 10. Updates

Tag a new version, run `store-apps` again, check the Play draft or the TestFlight build, and submit. Phones update automatically after review and release. A name, logo, colour, app id or domain change in the console reaches the store apps only through a new build; the console's store build card lists what changed.

### 11. Common problems

| Symptom | Fix |
|---|---|
| App cannot reach the server | `API_BASE` missing or wrong. Fix and rebuild |
| iOS signing fails | One of the three App ID capabilities is off |
| Play upload permission error | The service account needs release permissions on both apps |
| First Play upload fails through the API | Expected. Upload the first AAB in Play Console |
| Kakao or Google Android sign-in fails | Play app-signing SHA-1 not registered |
| No push | `GoogleService-Info.plist` or the APNs key is missing |
